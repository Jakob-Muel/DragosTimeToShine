# Evaluation prompts

Each prompt is standalone. Give one to an agent; it should investigate and report,
not change code.

---

## 2. Uncommitted work

> In this Godot repo, run `git status` and `git log --oneline`. Produce a report of every
> untracked or modified file, grouped by subsystem, and flag which ones are source of truth
> for shipped features versus generated/derived artifacts. Recommend a `.gitignore` and a
> commit split (which files belong in which commit, with messages). Do not commit anything.

---

## 3. main.gd god object

> Analyse `main.gd` (~2,245 lines) in this Godot 4 project. Map every `_show_*` function to
> the member variables it writes and the ones `_clear_screen()` resets. Report: which state is
> genuinely shared across screens vs. screen-local; which screens are fully independent and
> could become standalone scenes today with no shared state; and what the minimum shared
> layer (canvas fit, safe area, widget factories, screen router) would need to expose.
> Output a proposed file layout and a migration order, cheapest screen first. No code changes.

---

## 4. Hand-rolled layout

> This Godot 4 project builds all UI in code with hardcoded pixel coordinates on a 720-wide
> design canvas (`main.gd`, `DESIGN_WIDTH`, `_fit_design_canvas`, `_apply_responsive_rebuild`,
> `_safe_top_y`). Evaluate whether Godot's native systems — anchors, Containers, `SafeArea`,
> project stretch settings — could replace it. For each screen, say whether it maps cleanly to
> a Container tree or genuinely needs manual placement, and what the hardcoded values would
> become. Identify what breaks today at 750x1334 vs 1179x2556. Be concrete about the cost of
> conversion; if manual layout is the right call for some screens, say so.

---

## 5. Untyped dictionaries

> In this Godot 4 project, dragons and eggs are plain `Dictionary` objects with string keys
> (`scripts/game_state.gd`, `main.gd`). Find every read and write of these dictionaries and
> list the full key set with types and default values, noting where the same key is defaulted
> differently in different places (e.g. `get("species", ...)`). Then design typed `Resource`
> subclasses to replace them, and report how many call sites would change and which
> `.get(key, default)` calls are currently masking a bug. No code changes.

---

## 6. Save format

> Review save/load in `scripts/game_state.gd` (`SAVE_PATH`, `save_game`, `load_game`).
> There is no version field and `dragons.assign(saved_dragons)` trusts parsed JSON directly.
> Enumerate the concrete failure modes: old save meets new field, new save meets old build,
> corrupted/truncated file, hand-edited file, missing or wrong-typed keys inside a dragon
> dict. Propose a versioned schema with a migration path and validation, plus what should
> happen on unrecoverable load. Note whether the current code can lose data silently.

---

## 7. Art direction and animation

> This project's goal is an old-school Pokémon look (see the project brief). Inspect
> `assets/art/**` and every `texture_filter` / `TEXTURE_FILTER_*` assignment and import
> setting in the repo. Report: actual pixel dimensions and whether each asset is true pixel
> art or an upscale; where NEAREST and LINEAR filtering are used inconsistently (compare the
> ice island vs. the sunwing island in `_show_habitat`); and what the correct project-wide
> import defaults should be. Separately, describe the current dragon animation (a single
> TextureRect bobbed with `abs(sin())` in `_process`) and specify what a sprite-sheet setup
> would need — frame counts, states (idle/walk/eat/groom), and which code would change.

---

## 8. Test quality

> Review `tests/smoke_test.gd` in this Godot project. It drives the game via
> `scene.call("_private_method")` and `await create_timer(...)`. Identify every assertion that
> couples to a private name, internal field, or wall-clock delay, and say which would survive
> a refactor of `main.gd`. Then assess `scripts/game_state.gd` for unit-testability: list the
> pure-logic functions worth direct tests (steps→hatch, XP→level, contest gating, purchase
> rules) and the edge cases currently untested. Recommend a test layout and how to run it
> headless in CI. No code changes.

---

## 9. Screenshot bloat

> `docs/screenshots/` holds ~22 MB of tracked PNGs, regenerated by `tools/capture_screen.gd`.
> Evaluate options: keep and optimise (report achievable size after lossless/near-lossless
> compression and resizing), keep only a curated subset, move to a release artifact or
> branch, or generate in CI. Check which screenshots are actually referenced by any markdown
> in `docs/` and `README.md`, and list the orphans. Recommend one option with reasoning.

---

## 10. Signing config in VCS

> `export_presets.cfg` is tracked and contains `application/app_store_team_id="M3FS7LJM4P"`.
> Audit that file and `.github/workflows/` for every machine-, account-, or signing-specific
> value. For each, classify: harmless to commit, should be an env var / CI secret, or must
> never be committed. Recommend how a second developer would build iOS and Android without
> editing tracked files, and what belongs in a documented local override instead.
